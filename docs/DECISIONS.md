# Architecture decision records (concise)

Last reviewed: 2026-11-10. Decisions are revisable.

## ADR-001: Browser-first rather than MPC hardware
**Decision:** Responsive web app for Mac and Android; no required Akai MPC. **Reason:** immediate access and low friction. **Trade-off:** browser audio/CPU/device differences require testing. **Revised by ADR-012:** a Mac app comes next; the web app stays as the zero-install and Android path.

## ADR-002: Full-stack, not frontend-only
**Decision:** Python FastAPI backend on Vercel for DSP and AI orchestration, browser UI for recording/editing/export. **Reason:** safe server-only credentials and native DSP libraries. **Trade-off:** function CPU/runtime/bundle constraints. **Revised by ADR-011 and ADR-012:** the backend becomes an optional hosted mode and the local backend of the Mac app; tuning is planned to stay in Python there, and AI calls use the user's key kept in the macOS Keychain (AI.4). Moving them to the browser is only the later optional web-app path.

## ADR-003: Capability-specific, provider-neutral models
**Decision:** Portable project schema; configurable text LLM, on-device Basic Pitch transcription, WORLD tuning, future independent music-generation adapters. **Reason:** no single model does every job well. **Trade-off:** adapters/evals must be maintained. The present music-generation slot is not functional.

## ADR-004: Preserve the user's melody
**Decision:** Default melody lock on structured LLM edits, with undo. **Reason:** accompaniment instructions must not erase the original idea. **Trade-off:** intentional melody edits require the user to unlock; lock does not constrain every timbral/tempo change.

## ADR-005: Prefer open-source vocal tuning
**Decision:** WORLD vocoder using `pyworld-prebuilt` rather than licensing/repackaging Melodyne or Antares. **Reason:** portability, cost and control. **Trade-off:** quality and note editing are currently experimental.

## ADR-006: Stateless initial storage
**Decision:** Browser draft and portable JSON files; no cloud project DB on ephemeral Vercel functions. **Reason:** minimizes cost and complexity. **Trade-off:** projects/audio do not roam seamlessly across devices. **Extended by ADR-011:** still no Tandem server storage; durable storage is on the device and in storage the user brings.

## ADR-007: Tests and transparency
**Decision:** Python and Node CI suites plus real-device QA and explicit implemented-vs-planned documentation. **Reason:** READY deployments do not demonstrate audio quality. **Trade-off:** ongoing evaluation and fixture maintenance.

## ADR-008: Pitch-contour editor targets note centres
**Decision (VOX.3, 2026-11-10):** The editor stays note-based: one target pitch per detected note, drawn over the sung pitch line, with the server moving each note by its target minus its sung centre and keeping a chosen share of the vibrato (`vibrato`, editor default 100%, API default 0). Basic Pitch fragments are merged into whole notes in the browser; confidence stays client-side. **Reason:** dragging whole notes is what the roadmap asked for and what `/api/tune` can do statelessly; moving the note centre (not each frame) is what lets a target be dragged further than the old 250-cent cap and keep vibrato. **Trade-off:** no free-hand curve drawing or drift editing; the corrected line is a preview from Basic Pitch's contour, not WORLD's own analysis; the 100% default is unverified by ear until VOX.2.

## ADR-009: Access token lives for the tab only
**Decision (AI.3, 2026-11-10):** The browser keeps the shared access token in `sessionStorage` after a successful connection and deletes any `tandem-token` older versions left in `localStorage`. **Reason:** the token no longer outlives the tab or sits on disk for other users of the device, with no new server secret or session state. **Trade-off:** users re-enter it in each new tab; script on the page can still read it while the tab is open; an HttpOnly cookie session is deferred until there are real accounts.

## ADR-010: Harmony is a separate optional part
**Decision (ARR.1c, 2026-11-10):** Generated accompaniment is stored as an optional `harmony` note list with its own `harmony_instrument`, alongside `notes` and `drums`, in format version 1; no AI action edits it. **Reason:** the transcribed melody and melody lock stay intact, older projects stay valid, and the part is editable and exportable with the existing note tools. **Trade-off:** the AI can read but not change the harmony, and harmony does not follow later melody edits until it is generated again.

## ADR-011: Local-first, bring your own storage and keys
**Decision (STORE.1, operator-approved 2026-11-10):** Tandem is local-first and has no accounts for now. Everything a user makes lives on their device, and anything that leaves it goes to storage or a model provider the user chose and pays for.
- **On the device.** Projects and named versions move from `localStorage` to IndexedDB, and recordings are kept in the Origin Private File System (OPFS). The app asks for persistent storage (`navigator.storage.persist()`) so the browser does not evict them under storage pressure; where it is refused, the app says so and the user can export.
- **The user's own cloud storage, in order.** (1) The existing project file export/import. (2) "Save to folder" with the File System Access API, so a folder the user already syncs (Dropbox, iCloud Drive, Google Drive) carries projects between devices with no Tandem server; this works in Chromium desktop browsers only, so export/import stays the path everywhere else. (3) Optionally, the user's own S3-compatible bucket (for example Cloudflare R2 or Backblaze B2) with their own keys.
- **The user's own AI keys, called from the browser (revised by ADR-012: in the Mac app the key is kept in the macOS Keychain and used by the local backend, AI.4; the browser path below is the later optional web-app path).** OpenAI, Anthropic (which requires the `anthropic-dangerous-direct-browser-access` header for browser calls), Gemini, OpenRouter, and a local Ollama when it is configured to allow the app's origin. The checks `normalize_actions` and melody lock make on the server today are ported to the browser, so a model's reply is validated the same way whichever path it took. Keys kept in the browser require a strict Content Security Policy. The hosted `/api/chat` with the shared access token becomes optional.
- **On-device tuning.** WORLD (C++) is compiled to WebAssembly with Emscripten, and the `world_tuning.py` logic is ported, so `/api/tune` can run in the browser. With transcription, polish and tuning on the device, the app can be a static, offline-capable PWA; the FastAPI backend, Upstash rate limits and spend guards are then needed only for an optional hosted mode.
- **Not now.** Local-first sync frameworks are deferred; if multi-user collaboration becomes a goal, prefer Yjs or Automerge. No Rust rewrite.

**Reason:** no server-side user data to secure, store or pay for; no shared AI spend to guard; works offline; users keep ownership of their recordings. **Trade-off:** no seamless cross-device roaming without a synced folder or bucket; folder sync is Chromium-desktop only; browser storage can still be cleared by the user or evicted where persistence is refused; keys in the browser are exposed to any script that runs on the page, so XSS and malicious extensions become key theft (hence the CSP); each provider's browser (CORS) support must be checked and can change; a WASM build of WORLD adds a toolchain and must match the server's results.

## ADR-012: A Mac app with local models, for the biggest gain per unit of effort
**Decision (2026-11-10, operator-approved direction):** Tandem does not have to be a web app. The next work goes where it gives the most new capability for the least effort, in this order (ROADMAP sections 6 and 7):
- **Sampled instruments first (SND.1).** Recorded General MIDI instruments replace the synthesized tones in playback and WAV export. It is about a day or two of work, the most audible improvement available, and it helps the web app too.
- **A Mac app that reuses the existing code (DESK.1-DESK.4).** A small launcher (pywebview first) runs `tandem_backend.py` on `127.0.0.1` and shows `index.html` in a native window. It removes the hosted limits (Vercel's request size and duration caps, per-IP rate limits), saves projects as plain files (in place of STORE.2b), keeps AI keys in the macOS Keychain and uses the existing Python validation (in place of a JS port), and runs WORLD natively (in place of VOX.4). The local server binds to loopback only and checks the `Host` header (DESK.1) and requires a per-launch secret sent in a request header (DESK.2), with CORS limited to its own origin. This keeps web pages in the user's browser out, including through DNS rebinding; it does not keep out other processes running as the same user. The port is fixed so the browser storage that holds the draft (IndexedDB, OPFS) stays on the same origin between launches, and the web view uses persistent storage.
- **Local AI audio models (MODEL.1, SEP.1, GEN.2, TIMBRE.1).** Demucs separates a voice from background music, MusicGen-Melody generates a backing band that follows the user's own melody, and RAVE turns a voice into an instrument. They run on the Mac, which serverless functions cannot do. Their output is always a new, removable part, never a replacement for the user's idea (ADR-004).
- **Hand-off moves up (EXP.1).** Stems and multi-track MIDI for GarageBand and Logic, which the operator uses to finish work.
**Rejected:** a DAW plugin, or a C++ audio engine such as Tracktion Engine (JUCE): weeks of native work to rebuild what GarageBand and Logic already do, with no web path and possible GPL obligations. Suno and Udio: no official public API was found.
**Trade-off:** the Mac app is macOS only (the web app stays for Android and zero-install use, so both must keep working); a signed, notarized build needs a paid Apple Developer account (DESK.4); the models are large downloads and slow without Apple silicon. MusicGen's weights are licensed CC-BY-NC 4.0 (non-commercial), and the Demucs v4 weights' license is unclear, so commercial distribution needs a decision first (LIC.1). ADR-011 still holds (no accounts, the user's own storage and keys); the browser-only storage and key items it planned (STORE.2b, STORE.2c, the browser path of AI.4, VOX.4) are parked, not dropped.

## ADR-013: Capture song ideas on the phone with the web app
**Decision (2026-11-10, operator-approved direction):** Tandem gets a phone experience for catching song ideas the moment they come: open, tap, sing, and the take is kept. It is built as the existing web app installed to the home screen, not as a native or Flutter app, and it comes before the rest of the Mac app work (ROADMAP section 5a, then section 6). The split is **capture on the phone, develop in the studio** (the Mac app or a desktop browser).
- **A capture screen in the same app (MOB.1).** One large record button; every take is saved on the phone at once (OPFS and IndexedDB, as in STORE.2a) as an idea with its time and an optional name; ideas are listed, played, renamed, deleted and opened in the studio. It is part of the same origin, so ideas share the studio's storage, and it works without the network, an account or a server.
- **Offline and installable (MOB.2).** The service worker keeps everything capture needs, the manifest gets the icons iOS and Android need to install it, and the app asks for persistent storage. Safari may delete a site's storage after some days without a visit; installed home-screen web apps are treated differently, which must be checked on a real iPhone (MOB.4).
- **Ideas leave the phone as files (MOB.3).** With no accounts (ADR-011), an idea is shared as a file through the system share sheet (AirDrop, Files, iCloud Drive) and opened in the studio. The file is the project and its recording, the same content the Mac app saves as a project folder (DESK.3), so an iCloud Drive folder carries ideas from phone to Mac with no Tandem server.
- **Tuning on the phone comes later.** Capture needs only recording and storage; on-device transcription (Basic Pitch) already runs in the browser. Pitch correction still needs `/api/tune` until WORLD runs in the browser (VOX.4), which this decision moves back from parked to planned after the capture work.
**Rejected:** Flutter: it draws its own UI, so it would mean rewriting the studio (piano roll, Web Audio playback and export, Basic Pitch, IndexedDB/OPFS storage) in Dart, or wrapping the same WKWebView the web app already runs in; its audio support is weaker than Web Audio for scheduled synthesis and offline rendering. A native iOS app (Swift): a second codebase and App Store distribution before the idea is proven. Both stay possible later if the web app cannot do what capture needs on a real phone.
**Trade-off:** iOS stops microphone capture when a web app goes to the background or the screen locks, so a take ends there (to be confirmed in MOB.4); browser storage on a phone can be cleared by the user or the system, which is why sharing an idea out matters; the web app must work well in Safari on iOS, which the automated tests cover only through Playwright's WebKit, not a real iPhone. The Mac app (ADR-012) is unchanged in direction; DESK.2-DESK.4 follow the capture work.
