# Testing and release-quality checklist

Last reviewed: 2026-11-10. **Test files exist; passing CI status and real-device outcomes are not assumed.**

## Automated suites

```bash
python -m pip install -r requirements-dev.txt
python -m pytest -q
node --test tests/transcription.test.mjs tests/polish.test.mjs tests/tuning.test.mjs tests/history.test.mjs tests/versions.test.mjs tests/contour.test.mjs tests/groove.test.mjs tests/voices.test.mjs tests/harmony.test.mjs tests/phrases.test.mjs tests/storage.test.mjs tests/recordings.test.mjs tests/samples.test.mjs

# Browser end-to-end (needs a Playwright Chromium)
python -m pip install -r requirements-e2e.txt
python -m playwright install chromium
python -m pytest e2e -q
```
GitHub Actions workflow: `.github/workflows/tests.yml` triggers all three suites (`backend`, `transcription`, `e2e`) on pushes to `main` and pull requests. Inspect https://github.com/ogoldberg/tandem-music/actions for actual run state. The Vercel build status READY means packaging succeeded, **not** that all tests passed.

Python tests cover API health/config, token access, musical action validation, bad-model responses, provider adapter mocks, audio WAV validation, sine/silence transcription, pitch correction routines, WORLD pitch-target/quantization logic (including VOX.3's note shift, Keep vibrato, the stray-frame cap, the `vibrato`/`scale` parameters of `/api/tune`, and a check that the server still matches the shared preview fixture), the VOX.1 pitch-correction benchmark (`tests/test_vocal_benchmark.py`; thresholds and metrics in [AUDIO.md](AUDIO.md#pitch-correction-benchmark-vox1)) and WORLD timing (a tuned clip keeps its length, level and note positions throughout). Node tests cover named versions (`tests/versions.test.mjs`: save/list/restore/delete, reload persistence, name and project validation, the 50-version cap, a full quota, unreadable storage, and unrecognised entries kept through save and delete without counting towards the cap), Basic Pitch event conversion and its project-melody vs vocal-target limits (with an injected Basic Pitch module), 48,000 → 22,050 Hz resampling using a mocked OfflineAudioContext, and chunked tuning (`tests/tuning.test.mjs`: chunk plan within the request caps, note targets offset to each chunk, exact reconstruction, no clicks or level gaps at seams, 429 retry), on-device polish (`tests/polish.test.mjs`: parity with the original SciPy output at 16 and 44.1 kHz, filter response, a 5-minute recording, input validation), the pitch-contour editor model (`tests/contour.test.mjs`: Basic Pitch frame timing and contour pitch, note centres, scales, snapping and scale-degree steps, fragment merging, edge resizing, and the correction preview against the server's output on `tests/fixtures/target-correction.json`), and the edit history (`tests/history.test.mjs`: undo/redo order and labels, redo cleared by a new edit, no-op edits skipped, the size cap, and `rewrite` dropping edits that became no-ops).

Browser end-to-end tests (`e2e/`, CI.2) start the real app with uvicorn and drive headless Chromium through Playwright: load `/`, import a 48 kHz WAV of three tones, transcribe with the server fallback (`/api/analyze`, expecting MIDI 69/72/76), remove a note and undo, add a note and a drum hit, play and stop, export WAV (checked non-silent), MIDI and project JSON, clear and reopen the saved project, and reload to restore the localStorage draft. A second test (EDIT.1) walks one history through Load example, removing a note, instrument and tempo changes, an AI chat reply (the real chat form and action applier, with only the `/api/chat` response fulfilled by the test because CI has no provider credentials), and Open project; it undoes and redoes all of them with the buttons, Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z and Ctrl+Y, checks that Ctrl+Z in a text field is left alone, that a new edit clears redo and a no-op edit is not recorded, then detects sung notes with on-device Basic Pitch, undoes/redoes a vocal target arrow-key step, and checks that a new recording drops the old targets from history. A third test (PERF.3) imports a 3-minute WAV of held sung-range tones and runs real on-device Basic Pitch through Detect sung notes, expecting more than 128 targets, targets past 170 s and over 100 after 60 s; it takes about 2 minutes. The fixtures launch Chromium with `--enable-unsafe-swiftshader` so GPU-less machines such as GitHub runners still get software WebGL; without it TensorFlow.js falls back to its CPU backend and the test times out at "Detecting vocal notes…". A VOX.3 test detects the three tones on device and checks one target per tone at the sung pitch, each with a confidence, then drags a target up two semitones, drags another's end edge, steps a target with the arrow keys, picks C major and snaps (the A♯/B tie goes to the sung A), steps by scale degree, deletes and undoes, and confirms the `/api/tune` request carries exactly the edited `m`/`t`/`d` targets (no confidence) and the Keep vibrato amount before tuning completes. It then deletes every target and checks that Tune is disabled with a message pointing to Undo / Reset note edits, and that Undo, Redo and Reset note edits switch Tune back on and off (issue #23). A fourth test (EDIT.2) saves two named versions, rejects a blank name, restores one (checking notes, drums and tempo) and undoes the restore, reloads to confirm versions persist, and deletes one; another restores a hand-edited version without tempo or instrument and gets 100 bpm and piano. An ARR.1 test checks the empty-project messages for Quantize and Detect tempo, detects 133 bpm on the example, quantizes to 1/8 with 100% swing (notes on the beat, offbeat hits at two thirds of the beat, and the exported MIDI's drum hits on ticks 0, 640, 960, 1600), checks that quantizing again records no edit, and undoes both. An AI.3 test checks that a `tandem-token` left in `localStorage` by an older version is deleted on load, that a successful connection keeps the token in `sessionStorage` only, that it survives a reload but not a new tab, and that connecting with an empty field forgets it. A DESK.1 test (`e2e/test_desktop.py`) starts the Mac app launcher's own server (`tandem_desktop.start_server`, with its Host check) and loads the studio with no page or console errors, checking that `/api/config` reports the desktop runtime; Chromium stands in for WKWebView, so the native window, the microphone rule and storage across relaunches are manual QA. `tests/test_desktop.py` covers the kept port, a damaged settings file, the loopback-only bind, the Host check and the microphone rule without pywebview. A test fails on any uncaught page error or `console.error`. They do not cover Basic Pitch melody transcription, microphone recording, polish, the sound of tuned audio, or AI chat against a real model, and headless Chromium is not a substitute for the real-device matrix below. When the CI e2e job fails it uploads two artifacts: `e2e-traces` (Playwright traces) and `e2e-server-log` (the uvicorn log). Locally the log goes to a pytest temporary directory; set `E2E_SERVER_LOG=<path>` to keep it somewhere known. `python -m pytest` without a path runs only `tests/` (see `pytest.ini`).

An ARR.1b browser test plays and exports the example with each of the eight melody instruments and checks that every WAV is audible, below clipping and different from the others, that the chosen instrument survives a reload, and that opening a project with an unknown instrument is refused.

SND.1 tests: `tests/samples.test.mjs` covers the sample planning (nearest root, playback-rate shift, levels, loop points, release) and loading against a fake audio context; `tests/test_api.py` checks that the `/vendor/gm-samples-1/` route serves only files listed in `SHA256SUMS`, that the served bytes match the hashes and that the license file is present. The browser test `test_instruments_play_from_samples_and_fall_back_to_oscillators` exports every instrument from samples and again with the sample route blocked, checks the two differ and that the fallback is reported in the status line. Whether the samples sound good is a listening judgement not yet made on real speakers.

An ARR.1c browser test checks the message when there is no melody, generates chords for the example (C major, C C, triads E3-G3-C4), plays it, checks the exported MIDI has the triads on channel 2 at ticks 0 and 3840 with the melody untouched on channel 1 and that the WAV changes but does not clip, removes a harmony note and undoes it, generates a bass line in a chosen A minor while keeping a chosen organ, saves and restores a version, saves a project file, reloads, opens a pre-harmony project (no harmony, piano) and refuses an unknown harmony instrument. Node tests (`tests/harmony.test.mjs`) cover key detection on major and minor melodies, the diatonic chord lists, I-IV-V-I chosen under a melody that outlines it, voicing range and the exact voice-led triads, the bass pattern, bar timing at other tempos and start offsets, a chosen key, empty bars, the doubled downbeat weight, the 1024-note cap and input validation.

An ARR.1d browser test checks the empty phrase list, finds one phrase in the example, generates chords, chooses the phrase (its eight notes are marked), checks that moving it before the start is refused without an edit, copies it to the end (two bars later, a second phrase that becomes the choice), transposes the copy up an octave, moves it a beat later and down a semitone with phrase 1 and the harmony unchanged, undoes and redoes through them (undo clears the choice), and checks that raising the tempo splits a melody with a 0.5 s rest into two phrases. Node tests (`tests/phrases.test.mjs`) cover the rest threshold and its millisecond tolerance, tempo scaling, notes bridged by a long note, invalid notes, move/transpose/copy results and array order, the 0 s, 600 s, MIDI-range and 1024-note limits, bar-aligned copies that keep a pickup's place in the bar, and stale phrases.

STORE.2a browser tests check that a draft and versions left in `localStorage` move into IndexedDB (and leave `localStorage`), that later edits and versions survive a reload and a full browser restart (a persistent Chromium profile closed and reopened), that unparseable old versions are reported and kept, that unreadable versions already in IndexedDB are reported while the draft still migrates and saves, that the page ignores input until the stored draft is read, that the studio still works and says nothing is saved when IndexedDB is missing, and that the key-value store's updates are atomic in Chromium's IndexedDB. The draft helper reads IndexedDB directly. Recording tests (Chromium's OPFS) check that an imported recording and its polished take come back after a reload byte for byte, that each version restores its own recording while a version saved without one keeps the current one, that deleting a version deletes recordings nothing else links to, that a missing file is reported, that a quota error while writing is reported and leaves no file, and that without OPFS the studio still records and says the recording is not kept. `tests/recordings.test.mjs tests/samples.test.mjs` covers the store against fake OPFS directory and Web Locks objects.

## Audio test requirements
Generate controlled dry solo singing samples with known MIDI pitches/timing, multiple sample rates and realistic consonants, vibrato and noise; preserve consent and privacy. Test 0% strength equivalence, clipping, silence, note overlaps and transitions. Measure pitch error, duration, loudness, artifacts and listener preference. Verify quality against real human vocals—synthetic sines alone are insufficient.

## Release gate
- CI green, no unresolved deploy/runtime errors, health endpoint 200.
- Frontend assets load; no uncaught JS errors, including sample-rate or model-import errors.
- Key user journey passes Mac and Android.
- No accidental billing exposure: unauthorized chat requests rejected; public CPU routes rate-limited before broader distribution.
- Documentation updated with behavior, limitations, model dependencies and verified outcomes.
